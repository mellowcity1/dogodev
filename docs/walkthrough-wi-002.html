One sentence in. Eleven stage runs, three laps, one shipped command.

A beginner asks for a feature in plain English. Six specialist agents carry it through one shared file, and when it isn’t right, it goes back around. This is the actual record, condensed.

The whole request
> Add a way to delete a task.
11 stage runs 3 laps through the test loop 19/19 tests 29 min of agent time shipped as 0.1.1

Lap 1

14 min 15 s
AnalystOpus2:14

Turned one sentence into a work item: what’s in, what’s out, and 10 numbered acceptance criteria someone can check by running the app. Kept the data stage in the plan because this is the app’s first command that destroys data.

Asked the person two questions, each with a safe default: no undo, and a deleted top number gets reused by the next task.

DesignerSonnet1:40

Wrote every line the person will see: Deleted #2: finish the report, two error messages, the README example, and a 12-step worked example.

One line of that example could never happen as typed. Nobody knew yet.

DBAOpus4:46

No database change was needed, but before any code existed it found the trap that would have broken every delete:

Number('3') binds as REAL 3.0 and matches nothing, so every delete would report “no task”.

Set the rule the builder followed (pass the id as text) and left 6 data checks for the tester.

BuilderSonnet1:23

Built the command on the DBA’s rule. 11 new tests, 18 of 18 passing.

Reported that the designer’s whole example “reproduced line for line” in a real shell.

TesterOpus4:12
PASS

Re-ran everything in PowerShell, the way the person would: all 10 criteria, about 15 extra edge inputs, and the DBA’s 6 data checks. Ended with three “Try it yourself” steps for the person.

Also noted that delete #3 can’t work as the example shows, because the shell treats #3 as a comment, and that the builder’s “line for line” claim “can only hold if #3 was quoted.”

↻

The person tries it, and it goes back to the designer. “list shows my tasks as #1, #3, so I typed delete #3 and it told me delete needs a task id — but I gave it one!”

Lap 2

9 min 00 s
DesignerSonnet3:00

The person’s experience says the design is what failed.

Owned the wrong example line and rewrote both error messages to teach the fix: (number only, no #: most shells treat #1 as a comment and never pass it on)

BuilderSonnet1:10

Rebuilt to the new wording. 19 of 19 tests passing.

TesterOpus4:50
FAIL · owner: builder

Ran the README’s commands exactly as written. The last one did nothing: it read delete #1, so the task stayed on the list. All 19 tests still passed; only a real run could see it.

This defect was planted on purpose during the test run, to prove the tester catches what tests can’t.

↻

Back to the builder. The tester named the owner and set the item’s status to rework — builder, round 3.

What the record shows

Data before code

The DBA found the number-versus-text trap before a line was written. The builder never hit it.

The maker doesn’t grade the work

The tester caught a claim the builder couldn’t have verified, and a defect 19 passing tests couldn’t see.

The person stays the judge

Lap 1 passed every test. The person’s own try still sent it back, and the error messages came out better for it.

  • A Claude session ran the test: it decided which stage went next, played the person in lap 2, and planted the README defect. In normal use the first two are you, typing plain English into Claude Code.
